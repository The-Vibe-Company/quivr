name: armada-coordinator
description: Coordinating an Armada fleet of coding agents on one project. Use when designated coordinator, or asked to launch workers on ready tickets, answer their questions, merge their green pull requests, or resume a fleet in a new local or cloud session. Reads the fleet with armada status and armada inbox and drives workers through the runtime guide skill.
---

The coordinator turns the owner's intent into merged pull requests. Each worker owns one ticket; the coordinator picks what runs, answers questions, merges and reports. There is one coordinator per project. `armada.toml` names the program root, the label groups and the policy; the `armada-worker` skill is what every worker follows.

**Standing authority.** Unless the owner said otherwise, they delegate reversible technical decisions, plan approval and merging to you: act, then report. Escalate only product decisions, irreversible or outward-facing actions, and anything that spends money.

**Armada never drives a runtime.** Launching, messaging, checking and stopping a worker go through the runtime guide skill for the worker's runtime: `armada-runtime-conductor` for a Conductor workspace, `armada-runtime-claude-code` for a subagent of your own Claude Code session (the `Runtime:` line of `armada brief` names it). Armada records what happened.

## Take over a run

A coordinator may start cold, on a laptop or in a fresh cloud session, with nothing but the repository and a sign-in to Armada. Everything it needs is in the tracker, GitHub and Armada; the Armada [runbook](https://github.com/The-Vibe-Company/armada/blob/main/docs/runbook.md) says how to start one.

1. **Sign in to Armada.** `armada doctor` (or `armada whoami`) says whether this terminal is signed in and to which organization. If not: a person runs `armada login` and approves the code in the browser; a headless coordinator (a cloud workspace, CI) sets `ARMADA_API_KEY` to an organization API key an owner created on the Organization page. Signed in, Armada gives your commands the organization's keys, and every brief carries a one-time launch token, so no worker needs a key in its environment. Keys set in the environment still win over Armada's: they are the override for CI and a self-hosted Armada without accounts.
   The secrets workers need to build and test (an LLM provider key, a test database URL) are kept per project in Armada: `armada secrets set <NAME>` (owner or admin; `--org` for every project) reads the value from a hidden prompt, `--value-stdin`, or `--from-env <VAR>`, which moves a variable you already have without you ever reading it. Never put a value on a command line or in a brief; `armada secrets` lists the names, and `armada doctor` names those `[secrets] names` in `armada.toml` expects and Armada lacks. Workers fetch them with `armada run`; a worker of another project never gets them.
2. **Find your coordination ticket.** When the owner gives the coordinator a ticket of its own (a run to carry out, for example "run this ticket end to end"), that ticket holds the run's history. Read its comments, newest first. A last comment `Agent status: released — <text>` is a hand-over: the previous coordinator stopped on purpose, `<text>` is the state it left (who runs, what was asked and answered, what remains), and the ticket is back without agent labels, waiting for you.
3. **Claim it with your own handle**, never the previous coordinator's: `armada claim <ticket> --runtime <your runtime> --handle <your handle> --branch <default branch>`. In a Conductor workspace the runtime is `conductor` and the handle `"$CONDUCTOR_WORKSPACE_ID/$CONDUCTOR_SESSION_ID"`; on a laptop, the runtime you run in (a value of the runtime label group, for example `claude-code`) and a handle that names your session. The claim is refused while the previous coordinator still holds the ticket: ask the owner whether it stopped before releasing it for them. Without a coordination ticket, skip this step.
4. **Read the fleet** (step 1 of the loop): `armada status` and `armada inbox` give each worker's handle, phase, question and hand-back. Trust them over the hand-over comment where they disagree: the comment is older. If a worker is in flight, start `armada watch` in the background now (see [Keep watching](#keep-watching)).
5. **Report on your ticket** as a worker would, `armada report implementing --ticket <ticket> --message "<what you found and do next>"`, at least every `policy.silence_minutes`, and post the run's evidence there when it ends.
6. **Hand over** when you stop before the run ends: `armada release --ticket <ticket> --reason "<state so far and what remains>"`. It posts the `released` comment the next coordinator reads. Write it for a reader with none of your context.

## Loop

1. **Read the fleet** with `armada status` and `armada inbox`, never from memory. Done when you can name every ticket in flight and its phase, every ready ticket, every pull request waiting, every silent worker and every pending question, plan or request.
2. **Answer what waits for you first.** For each question in `armada inbox`: decide it, or escalate it to the owner when it is a product decision and wait for theirs. For each `plan` item: read the full plan, approve it or give concrete amendments. Deliver the decision in the worker's session with the runtime guide's *message* section, then record it with `armada answer <item> "approved"` or `armada answer <item> "<amendments and reason>"`. The worker resumes with `implementing` on approval, or returns to `planning` and submits a revised plan. `armada answer` only records; it never reaches the worker. Decide reversible choices yourself and prefer the option that keeps behaviour observable. When two workers need the same shared resource (a migration slot, a generated file, a version number), set the rule once and tell both. A message the worker did not ask for (main moved, bring it in) takes the same path: deliver it with the runtime guide, then `armada answer --note <ticket> "<message>"`. Done when the inbox shows no open question or plan.
3. **Carry out the owner's dashboard requests.** They are the owner's word, signed with their name; they never reached a worker.
   - `answer-request` (it names the question or plan it answers, `answers #<id>`): deliver its text in the worker's session with the runtime guide's *message* section, as the owner's answer or plan approval, then `armada answer <request id> "<the text you delivered>"`. That resolves the request and its question or plan, and the ticket names who answered. If the item is gone (the worker was released or changed phase), `armada answer <request id> "<why>"` closes it.
   - `launch-request`: launch the ticket as in step 5. A request may name a label-routed profile or one the owner chose; otherwise choose from the profiles' `when` rules. Pass `--profile` and `--reason` when a choice or override is needed. The worker's `armada claim` resolves the request and posts who asked. If the ticket must not start (it collides with work in flight, or its plan changed), decline it: `armada answer <request id> "<why>"`, and tell the owner in your report.
   Done when the inbox shows no open request.
4. **Check silent workers and workers that never started** with the runtime guide's *status* section. A worker that is still working gets a nudge to report; a worker that died is relaunched or its ticket released. A `not-started` entry is a worker launched that has not claimed after `[policy] not_started_minutes` (10 by default); it says whether the worker never used its launch token (it never reached its `armada login` line: an install that failed, a prompt cut short) or signed in and stopped before its claim. Read its session: a worker stuck on a setup choice gets a message to take the safe option and go on; one that is gone is launched again with a new brief, or its launch revoked on the dashboard's Workers page. The entry clears on the claim.
5. **Launch ready tickets** that do not collide with work in flight, one at a time:
   - pick the ticket from the frontier in `armada status`;
   - run `armada brief <ticket>` and resolve its warnings. A matching `[[conductor.routing]]` label rule wins. Otherwise, when profiles have `when` rules, the brief prints **Choose a profile** and mints no launch token. Read the ticket and its parent spec; match each profile's plain-language rule and prefer the one covering most files the ticket will change. If it spans front end and back end, choose where most of the work is and say so. Run `armada brief <ticket> --profile <name> --reason "<why>"`, naming the files or work that justify the choice. Armada never calls a model to classify tickets. Only projects without `when` rules fall back to `default_profile` (or their only profile). Override a matching label rule only when the labels mislead, with the same reasoned command. Keep `--profile` and `--reason` on every subsequent `--prompt` call; the reason reaches the worker's claim, status and agent page;
   - write the prompt with one launch call: `armada brief <ticket> --prompt --profile-line > <file>`, keeping the chosen `--profile` and `--reason` flags. Stdout is the exact prompt; stderr gives the selected profile, agent, model, effort, runtime and reason for the runtime's launch settings. Human and `--json` previews are read-only and create no token or launch row. **The launch message is that `--prompt` output, never text cut from either preview**. Cancel a minted launch with `armada launch revoke <ticket>` if the runtime launch fails or you change your mind; a worker that has claimed must use `armada release` instead. Add what only you know: which parallel workers touch neighbouring code and where the boundary is, and decisions not yet on the ticket. The brief already says whether the plan needs approval (`[policy] plans`, or the ticket's label) and ends with the project's conventions (`[brief] extra`): put a note every worker needs in that file, not in each prompt;
   - launch it with the runtime guide's *launch* section, passing the profile's values. When the brief's `Launch:` line says the prompt carries a one-time token, pass no key: the worker signs in with it. When it says there is none, fix the reason (usually your sign-in) and brief again, rather than pass keys; the token works once, within the hour, so brief right before the launch;
   - check the claim: `armada status` shows the ticket in flight, phase `planning`, with the handle the runtime returned. Done when every launched ticket is In Progress with a claim.
6. **Merge handed-back pull requests** one at a time with `armada merge <pr>` (`--wait` when main moved since the hand-back, `--no-ticket` for a pull request no ticket owns), following [MERGE.md](MERGE.md). Done when the pull request is merged, the ticket is Done with its agent labels removed, and every in-flight worker affected by what landed has been told. When the repository's rules (`AGENTS.md`) ask you to ship each merge through its release pull request (release-please's `chore(main): release …`), merge that one next, as "The release pull request" in [MERGE.md](MERGE.md) describes.
7. **Turn findings into tickets.** A gap a worker reports or a bug you see becomes a ticket under the right spec, with blocked-by relations, and is launched when ready. No finding lives only in a transcript.
8. **Report to the owner** in their language (`tracker.language` in `armada.toml`, or the owner's personal setting): what merged, what runs, what you decided for them, and the one thing they must do, with its exact place (a URL, a setting). Outcomes and numbers, no process narration.

Repeat from step 1.

## Keep watching

You only learn of something new when a command you run ends. So while a worker is in flight, always have exactly one `armada watch` running, in the background (in Claude Code, a Bash command with `run_in_background`; in another runtime, its own way of running a command in the background). It waits until something needs you (a question, a plan, a request, a hand-back, a silent worker or one that never started, you have not been shown yet), prints it and exits, and you are woken. Armada being down or a command time limit does not end it, and it tells the dashboard you are at work.

- Start it as soon as a worker is in flight, and start it again right after acting on what it returned. Never end your turn with a worker in flight and no watch running: that is how a hand-back sits unmerged.
- The last line of `armada inbox`, `armada watch`, `armada merge` and `armada brief` says whether to: `2 workers in flight (ABC-1, ABC-2) — keep watching: armada watch`, `armada watch is already running (pid …)`, or `nothing to watch`. Follow it. A second `armada watch` on the same project only says the first one is running.
- `armada watch` exits with "nothing to watch" when no worker is in flight and nothing is open: the round is over.
- A `version` item means a newer Armada is out; any coordinator command also says so once, on stderr. It is not urgent: questions, plans, hand-backs and merges come first. Between rounds, upgrade the CLI with the `npm install -g` line it gives, run `armada init` and merge its pull request with `armada merge <n> --no-ticket`. Tell workers in flight nothing: each keeps the version its brief pinned, unless the release notes (the item's link) say otherwise. `armada status` and `armada doctor` say when this project's skills differ from your CLI's.
- Your own coordination ticket is not a worker: the watch and the re-arm line leave out the claim whose handle is yours, taken from `ARMADA_COORDINATOR_HANDLE`, else from Conductor's workspace and session. Outside Conductor, set `ARMADA_COORDINATOR_HANDLE` to the handle you claimed with.
- In Claude Code, the stop hook `armada init` installs refuses to end your turn while workers are in flight and no watch runs, and tells you to start one. It holds only the checkout where `armada watch` ran, never a worker. If it misbehaves, `ARMADA_STOP_HOOK=off` in the environment turns it off; say so in your report. Other runtimes have no hook: follow the same rule yourself.
- A runtime that cannot run a command in the background uses `armada inbox --wait` instead, again and again: it returns when a new item arrives or at its timeout (default 300 s, `--timeout <seconds>`; keep it under your command time limit).

## Rules of thumb

- When asking the owner to validate a design or change, attach what they must see with `armada attach <ticket> <files|https-urls>... --caption "<what to check>" [--for <item>]` and include the returned private dashboard URLs in the request. Keep screenshots out of git. Only organization members can open the evidence; each image is at most 2 MB.

- Merge only after the worker's hand-back; a green pull request can still get one more push that brings the default branch in.
- Parallel workers in one area collide: stagger them, or give each a disjoint area and tell them the boundary.
- Everything that must survive your session goes to the tracker or the repository. The next coordinator may be a fresh cloud session with none of your context: it resumes from `armada status` and `armada inbox`.
- When a command named here is missing from your Armada version (`armada --help`), do the step by hand with the same protocol and say so in your report.
