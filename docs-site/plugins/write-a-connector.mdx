A connector plugin adds a kind of Connector Instance, so Quivr can collect from a source it does not know yet. This page builds `folder_notes`, a kind that collects the `.txt` files of a folder, one Record per file.

## Prerequisites

- Go 1.24 or later, a `quivr-v2` checkout in `$QUIVR_REPO`, and the `quivr` command on your `PATH` ([Build your first plugin](/plugins/first-plugin) shows how).
- Read [How plugins work](/plugins/overview) for what Quivr keeps and what the plugin decides.

## How a run works

On each instance's schedule, the Quivr worker calls `fetch` with the instance's configuration, its decrypted credential and the checkpoint the plugin returned last (`null` on the first run). The plugin answers a page of items and a new checkpoint. Quivr stores the items through the normal ingestion path and only then saves the checkpoint, so a crash never loses an item. With `more: true` Quivr asks for the next page at once, up to 10 pages per run.

The plugin keeps no state. Anything it must remember between runs, such as a cursor or the revisions it already returned, goes in the checkpoint, up to 64 KiB.

<Steps>
<Step title="Create the module">

The Go SDK is not published as a separate module yet, so point Go at your checkout:

```bash
mkdir folder-notes && cd folder-notes
go mod init example.com/folder-notes
go mod edit -replace github.com/The-Vibe-Company/quivr-v2/sdks/go="$QUIVR_REPO/sdks/go"
```

</Step>
<Step title="Declare the kind">

Each kind declares the JSON Schema of its instance configuration, and of its credential when the source needs one. Quivr validates both when an instance is created, and shows them to clients through `GET /v0/connector-kinds`.

```yaml quivr-plugin.yaml
id: acme.folder-notes
version: 0.1.0
description: Collects the text files of a folder.
compatibility:
  engine: ">=0.1.0 <0.3.0"
  plugin_api: ">=0.3.0 <0.4.0"
contributions:
  connector:
    kinds:
      folder_notes:
        description: Every .txt file of one folder, one Record per file.
        config_schema:
          type: object
          additionalProperties: false
          required: [path]
          properties:
            path: {type: string, minLength: 1}
        default_interval_seconds: 300
run:
  command: [go, run, .]
```

</Step>
<Step title="Implement fetch">

The checkpoint maps each file name to the revision already returned, so a run returns only new or changed files. Each item has a stable `RecordKey`; a new `Revision` for the same key becomes a correction, a new Version of the same Record.

```go main.go
// Command folder-notes is a Quivr connector: each .txt file of a folder becomes a Record.
package main

import (
	"context"
	"crypto/sha256"
	"encoding/hex"
	"log"
	"os"
	"path/filepath"
	"sort"

	"github.com/The-Vibe-Company/quivr-v2/sdks/go/quivrplugin"
)

type folder struct{}

// Fetch returns the files whose content changed since the checkpoint, which maps
// each file name to the revision Quivr already has.
func (folder) Fetch(_ context.Context, req *quivrplugin.FetchRequest) (*quivrplugin.Page, error) {
	var cfg struct {
		Path string `json:"path"`
	}
	if err := req.Connector.DecodeConfig(&cfg); err != nil {
		return nil, quivrplugin.SourceError("invalid_config", err.Error())
	}
	seen := map[string]string{}
	if err := req.DecodeCheckpoint(&seen); err != nil {
		return nil, quivrplugin.SourceError("invalid_checkpoint", "the checkpoint is not a map of revisions")
	}
	names, err := filepath.Glob(filepath.Join(cfg.Path, "*.txt"))
	if err != nil || names == nil {
		return nil, quivrplugin.TransientError("folder_unavailable", "the folder cannot be listed")
	}
	sort.Strings(names)
	page := &quivrplugin.Page{Checkpoint: seen}
	for _, name := range names {
		data, err := os.ReadFile(name)
		if err != nil {
			return nil, quivrplugin.TransientError("file_unavailable", "a file cannot be read")
		}
		sum := sha256.Sum256(data)
		key, revision := filepath.Base(name), hex.EncodeToString(sum[:])
		if seen[key] == revision {
			continue
		}
		if len(page.Items) == 100 {
			page.More = true
			break
		}
		seen[key] = revision
		page.Items = append(page.Items, quivrplugin.Item{RecordKey: key, Revision: revision, Content: quivrplugin.Text(string(data))})
	}
	return page, nil
}

// CheckCredential accepts: this kind takes no credential.
func (folder) CheckCredential(context.Context, *quivrplugin.CredentialRequest) (*quivrplugin.CredentialStatus, error) {
	return &quivrplugin.CredentialStatus{}, nil
}

func main() {
	plugin, err := quivrplugin.New("")
	if err == nil {
		err = plugin.Connector("folder_notes", folder{})
	}
	if err == nil {
		err = plugin.Serve()
	}
	if err != nil {
		log.Fatal(err)
	}
}
```

The error type tells Quivr what to show operators in the instance's health:

| Return | Meaning | Health |
| --- | --- | --- |
| `AccessError(code, message)` | The source refuses the credential or the access | `access_error` until a later run succeeds |
| `TransientError(code, message)` | An outage, a timeout or a rate limit; add `.WithRetryAfter(d)` when the source says when | unchanged; retried at the next run |
| `SourceError(code, message)` | The source returned data the plugin cannot use | the run fails |

A kind with a credential receives it decrypted in `req.Credential`. The SDK redacts it from logs and error messages, and the Contract Runner fails a plugin that echoes it.

</Step>
<Step title="Add a fixture">

A connector fixture names the kind, the configuration and what each page should return:

```bash
mkdir -p fixtures/notes
printf 'The harbour opens on Monday.\n' > fixtures/notes/harbour.txt
printf 'The market moves to Saturday.\n' > fixtures/notes/market.txt
```

```json fixtures/notes.json
{
  "description": "Two notes in one page, then nothing new when resumed.",
  "connector": {"kind": "folder_notes", "config": {"path": "fixtures/notes"}},
  "credential": null,
  "expect": {"pages": [{"record_keys": ["harbour.txt", "market.txt"], "more": false}]}
}
```

</Step>
<Step title="Certify it">

```bash
go mod tidy
quivr plugin test --startup-timeout 120s .
```

The first start compiles the plugin, hence the longer timeout. The runner fetches every page, feeding each checkpoint back, then starts a new run from the final checkpoint and fails if an unchanged item comes back:

```text
  PASS  resume           [connector] fixtures/notes.json: a new run from the final checkpoint returns no item already returned (0 ms)
CERTIFIED: the engine can safely invoke this plugin (17 passed, 0 failed, 1 skipped)
```

</Step>


`folder_notes` is listed next to the other kinds. Create an instance as for any kind, with `"kind": "folder_notes"` and `"config": {"path": "/srv/notes"}`: see [Collect from a source](/guides/connectors).

To add the plugin to a deployment that is already running, register it with its `fixtures/` folder instead of pinning it: Quivr runs the same checks, and you activate it without a restart. See [Upgrade or switch a plugin](/run-quivr/upgrade-a-plugin).

## Receive data through a Quivr key

For a push source, use a Plugin API range that admits `0.11.0`, declare
`modes: [pull, push]`, and add `api.routes` to the kind. This illustrative kind
fragment declares one JSON push route and one synchronous challenge:

```yaml
modes: [pull, push]
api:
  routes:
    - name: push
      method: POST
      path: events/{category}
      auth: quivr_key
      request_schema:
        type: object
        required: [text]
        properties:
          text: {type: string}
    - {name: challenge, method: GET, path: challenge, auth: quivr_key}
```

Implement `Receiver.Receive` in Go (or the language-neutral
`POST /v0/contributions/connector/receive` contract). Select the handler with
`req.Route`, decode the JSON in `req.Body`, and read template values from
`req.Request.Path`. Return stable Record Keys and revisions just as `Fetch`
does. For a POST, return an accepted `Delivery` with its items; Quivr ingests
them and returns `202` with their Receipts. For a GET challenge, return the
challenge response without items. The [plugin contract](/reference/plugin-protocol#connector)
lists the request and response fields.

Grant the caller's key `connector:push` on the instance's collection using the
[API key configuration](/reference/configuration#api-keys). A caller sends JSON
to `POST /v0/connectors/<instance_id>/api/events/news` with that bearer key.
The response's `receipts` array contains the normal ingestion Receipts; poll
those with a key that grants `content:read`. Missing keys, missing permission
or a different collection are refused before your plugin is called. A malformed
body is `400`, a schema mismatch is `422`, an undeclared path is `404`, and a
wrong method is `405` with `Allow`. Bodies are limited to 1 MiB. Rejected items
return `422 item_rejected`; retrying unchanged revisions replays items that
were already accepted. Transient failures return `503` with `Retry-After`.

Set the engine-owned `push_policy` when you create an instance to override its
request rate and burst capacity or restrict callers with `allowed_cidrs`.
Keep these fields separate from your kind's `config`. Defaults and trusted proxy
networks are set in [deployment configuration](/reference/configuration).
A rate refusal returns `429` with `Retry-After` before your plugin is called.
An address outside the allowlist returns `403 ip_not_allowed`.

Send an `Idempotency-Key` to replay the first completed answer for that instance
within the configured TTL, including its Receipts, without another plugin call.
Use a new key for a new delivery. Authentication, schema, IP and rate refusals
do not reserve a key. A completed plugin or ingestion failure is cached too;
after correcting its cause, retry with a new key and stable item revisions.

Every attempt on an existing instance records `connector.push.received` for a
2xx answer or `connector.push.refused` for another status. Cached replies and
GET challenges count as attempts. Events and per-instance counters commit
together; audit storage failure returns `503`. Read counters at
`GET /v0/admin/stats/connector-pushes` with `observability:read` on all collections.
The listing returns the largest 100 instance/outcome pairs and a total across all
pairs; use `limit` (1–100) to shorten it, or `connector_id` to read both outcomes
of one instance. Those two filters cannot be combined.

Quivr strips the bearer key and cookies before relaying the request. The existing public webhook address stays
available with its existing plugin-owned authentication.

## Receive data through an instance token

For a third-party sender, declare `auth: instance_token` on the route and use a
Plugin API range admitting `0.12.0`. The same `Receiver.Receive` handler and
route/body fields apply. Quivr authenticates the token before applying the same push protection policy
and calling your plugin; do not pass it to the handler or store it in the plugin configuration.

An operator issues and manages tokens under `/v0/connectors/<instance_id>/tokens`
with `connectors:admin`. Each token works only on that instance's token routes.
Quivr keys cannot authorize those routes, and instance tokens cannot authorize
Quivr-key routes or normal API reads. The [operator guide](/guides/connectors#give-a-third-party-a-push-token)
explains one-time issuance, five-minute rotation overlap and immediate revocation.

## Go further

A kind can also store binary attachments next to an item: declare `contributions.connector.attachments` and implement `OpenAttachment`, and Quivr asks for each file's size and checksum, then gives the plugin a one-time upload URL. A kind with `modes: [pull, push]` also receives the webhooks a source sends to Quivr, through `receive`; the X list connector works this way. The [plugin protocol](/reference/plugin-protocol#connector) lists every field of `fetch` and its answer, and the first-party `plugins/rss` is a complete connector built on this SDK.

## Verify provider signatures

For a provider that signs pushes, declare `auth: signature` and
`signature: {header, timestamp_header?, window_seconds}` on its POST route.
This requires Plugin API 0.12. Use a window between 1 and 86400 seconds.
If the provider signs a timestamp, name its Unix-seconds header; Quivr rejects
calls outside the window before invoking your plugin. Your handler still
verifies the cryptographic signature over the raw request before accepting
items. Preserve `request.body_base64` for that check.

The engine runs the signature freshness and replay guard before the instance's
IP allowlist and token bucket. A signature replay returns `409 push_replayed`.
Signature routes bypass the response cache: after the replay window expires,
every admitted POST or GET challenge reaches provider verification, even with
an earlier idempotency key. These protections and audit
counters also apply at a declared signature route's legacy receive alias.

Quivr reserves signature and `Idempotency-Key` fingerprints per instance in
PostgreSQL before calling your handler. A replay returns `409 push_replayed`;
invalid signature or timestamp headers return `401 invalid_signature`.
Reservations last for the window and are released on refusal or failed
processing within the request deadline so a valid retry can succeed. If the deadline expires or storage prevents cleanup, the reservation remains until its window expires and retries return 409 meanwhile. A provider without signed timestamps
has replay protection only within the cache window.

Declare a GET signature route for synchronous challenges. It bypasses POST
signature and replay guards, and must return no ingestion items. If your kind
has signature routes, its legacy webhook is an alias only for its declared
signature `receive` path. The first-party X plugin uses POST receive and GET
challenge on that path; its old address is scheduled for removal in engine 1.0.0.

For a source that receives records from a third party, start with `quivr plugin init <name> --kind connector --push` and follow [Receive pushed records](/plugins/push-source).
