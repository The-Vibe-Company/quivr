This section is for the operator: the person who deploys Quivr, chooses the plugins it calls, and keeps search and alerts working for the applications built on it. If you write an application that calls Quivr's API, start with the [Guides](/guides/add-content) instead.

## What you need first

- **A running Quivr.** On your machine, `make dev` starts one; see the [Quickstart](/quickstart). For your own servers, read [Deploy and configure Quivr](/run-quivr/deploy).
- **Its configuration file**, the JSON file named by `QUIVR_CONFIG`, and the right to restart the `api` and `worker` processes. Plugins, API keys and most limits are set there.
- **An operator API key.** Runtime plugin changes, backfills and vector space promotions need `plugins:admin`; following their progress needs `operations:read`. Each page lists the exact permissions it uses. The [API keys reference](/reference/configuration#api-keys) lists every permission.
- **`curl` and `jq`** for the requests on these pages.

Some changes need a restart and others do not. A change to the configuration file takes effect when the `api` and `worker` processes restart. Registering or activating a plugin, filling a vector space, reprocessing documents and retiring alert evaluations are API requests that apply while Quivr runs.

## Plugins

Plugins are separate HTTP services that read files, cut and embed passages, rank results and judge alerts. [How plugins work](/plugins/overview) explains their roles.

- [First-party plugins](/run-quivr/catalog): the plugins that ship with Quivr and their settings.
- [Pin a plugin](/run-quivr/pin): make Quivr call a plugin at startup.
- [Upgrade or switch a plugin](/run-quivr/upgrade-a-plugin): replace a plugin while Quivr runs, and roll back.
- [Reprocess quarantined documents](/run-quivr/reprocess-quarantined-versions): run the documents a plugin refused or failed on again, once it is fixed.
