---
title: "Upgrade Quivr and keep a rollback window"
description: "Apply compatible schema changes, roll the API and worker, and defer destructive cleanup."
keywords: [upgrade, migration, rollback, deployment]
---
Apply the new version's additive database changes while the previous API and worker keep running. Keep destructive cleanup deferred until you no longer need application rollback.

## Prerequisites

You need operator access to the deployment, the new and previous binaries, and their configuration files. Keep the previous configuration and plugin versions available. Your platform must run overlapping instances and route traffic to ready instances; Quivr does not provide the rollout controller.

Read the release notes for required backfills and contract migrations. Historical migrations classified as risks in the repository's `migrations/legacy.json` predate this rule; the rollback guarantee does not extend across those changes.

## Steps

1. Run the new binary's `quivr migrate` with `QUIVR_CONFIG` pointing to its deployment configuration. It applies pending expansions and required dependency setup, leaving tagged contracts untouched. Performance indexes are built concurrently by the API and worker after startup. They reuse matching valid indexes and retry interrupted builds in the background, allowing database writes to continue.
2. Roll the API instances. Wait for each new instance's `/readyz` to return HTTP 204 before routing traffic to it, then drain the previous instance. Keep at least one ready API serving throughout.
3. Roll the workers. Start a new worker and wait for its `/readyz`, then signal the previous worker to drain. Keep the compatible plugin versions available to both versions while work is in flight.
4. Observe ingestion, search and worker processing before ending the rollback window. Until you apply contracts, restore the previous binary and configuration using the same rolling process if the application needs rollback. Leave the expanded database in place.
5. Once all previous instances and their work have drained, and you accept closing the rollback window, run the new binary's `quivr migrate --contract`. This applies every pending contract as well as expansions; review all deferred steps before running it. The current application must already work with and without those contracts.

Do not run the previous version's migrator during rollback. Rollback switches application binaries; there are no hand-written down migrations. After contracts remove old fields or constraints, restoring the previous application is no longer supported. Recovery then needs a forward fix or your deployment's data recovery procedure.

Existing Corpora keep their keyword generation through an upgrade. Rebuild a
Corpus to enable item keyword fields and range-indexed dates; a successful
rebuild activates the new recipe. New Corpora use it immediately. Lexical and
hybrid searches across both recipes combine their reciprocal ranks before
applying the result limit, because their keyword scores use different populations.
Drain every previous API and worker instance before creating new Corpora,
writing content or starting rebuilds or retrieval configuration changes that
target the new recipe. Previous binaries cannot populate item keyword anchors,
even though they can continue serving historical generations.
Use your platform's rollout status to confirm that every old API and worker
process has stopped before enabling those writes.

The ingestion path prepares blob and embedding coverage writes before locking the organization's change journal. Upgrade every API instance and every live and bulk worker that writes to the database as one deployment. Wait until all previous processes finish draining and stop before relying on the improved import throughput. Previous writers acquire these locks in a different order and lack the bounded deadlock retries. New writers make at most three transaction attempts, including the first attempt, for a PostgreSQL deadlock. The third failed attempt returns the storage error to the caller; the `quivr.postgres.journal_deadlock` log event records `operation`, `attempt`, `retry_count` and `retry_exhausted`.

## Check it worked

The new API and worker report ready, ingestion resolves new receipts, and search returns the expected records. CI checks the previous version's inline ingestion, authorization and lexical search against the expanded schema, including a restart. Until versioned release artifacts supply the previous binary, CI uses the branch's merge-base commit; this is a focused compatibility check, not a complete release matrix.

Inspect the `X-Quivr-Index-Setup` header on `/readyz`: `pending`, `building`, `retrying` or `conflict` means performance is degraded while optional indexes are unavailable; `ready` means all expected indexes are valid. These states do not change readiness HTTP 204 when required dependencies are ready. Structured `quivr.postgres.index_setup` events report the state, attempt number and retry delay. Keep an API or worker running so setup can finish.

## Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| Migration times out | SQL migrations bound locks to two seconds and statements to five seconds; a failure rolls back their transaction. Let conflicting transactions finish, then rerun. Index maintenance uses a separate advisory lock. An index build started by an older binary can still hold the migration lock until it finishes or is stopped. |
| `index_setup_failed` or `index_setup_busy` in background events | Live processes retry with backoff from one second to one minute. Each attempt has a 30-minute budget and no separate lock timeout. Interrupted builds can leave invalid indexes; the next attempt repairs them. Required migrations and readiness proceed independently. |
| `index_definition_conflict` | A performance index name belongs to an object with a different definition. Inspect the database catalog and rename the conflicting object. Quivr leaves it untouched and detects your repair on a later attempt. |
| Worker never becomes ready | An expansion is pending or a dependency is unavailable. Run the new migrator and inspect startup logs. |
| Previous binary fails after cleanup | The contract step closed the rollback window. Deploy a forward fix or follow your data recovery procedure. |

Database writes can wait briefly for additive DDL locks. Compatibility requires both application versions to support the expanded representation; rollout and data backfills still need deployment-specific review.

An interrupted index build restarts from scratch on the next attempt. If index setup consistently exceeds 30 minutes, stop automatic index maintenance by draining the API and worker instances, then build the indexes concurrently in an operator database session with a longer timeout. Use the same index names, columns and predicates; remove a matching invalid index before rebuilding it. Restart the instances afterward to verify and reuse the indexes.

For the document-rebuild index, inspect the existing definition first:

```sql
SELECT indisvalid, pg_get_indexdef(indexrelid) AS definition
FROM pg_index
WHERE indexrelid = to_regclass('segments_by_segmentation');
```

In a separate database session outside a transaction, if the index is invalid and matches the definition below, run `DROP INDEX CONCURRENTLY segments_by_segmentation` first. Preserve any incompatible object and follow the conflict guidance above. In that same session, outside a transaction, allow up to two hours for the build:

```sql
SET lock_timeout = '0';
SET statement_timeout = '2h';
CREATE INDEX CONCURRENTLY IF NOT EXISTS segments_by_segmentation
  ON segments (organization, segmentation_id);
```

A valid matching index is reused; close this session afterward and restart the API and worker to finish index setup.
