A described alert fires when a new article fits a description such as "Labour strikes at ports and harbours", whatever words or language the article uses. An external classifier, TypeSafe's Jev, reads each new article and scores how well it fits. Described alerts are part of the first-party `alerts` plugin, next to [keyword alerts](/guides/keyword-alerts).

<Warning>
To judge an article, the plugin sends its title, its text (up to about 48 KB), its Source Namespace and any mapped metadata to TypeSafe's API. Without a TypeSafe key, described alerts are off and nothing is sent.
</Warning>

## Prerequisites

- An operator has turned described alerts on ([below](#turn-them-on)).
- Everything the [keyword alerts](/guides/keyword-alerts#prerequisites) guide needs: an API key with `monitoring:write` and a webhook destination.

## Write a description

Describe the subject of the articles you want in one or two plain sentences, 3 to 1000 characters.

| Good | Why |
| --- | --- |
| `Labour strikes at ports and harbours` | One subject, stated directly |
| `New rules on electric scooters in cities` | Specific enough to leave out other transport news |

Write one alert per subject, and say what fits rather than what does not: the classifier reads negations literally. English descriptions work best, and they also find articles in other languages.

## Save the alert

The expression holds the description. `sources` is optional: it limits the alert to some Source Namespaces, and articles from other sources are never sent to the classifier.

```json
{"kind": "described", "description": "Labour strikes at ports and harbours", "sources": ["wire"]}
```

Create a Saved Query with this expression and a Subscription with the `alerts` evaluator, as for a [keyword alert](/guides/keyword-alerts#save-the-alert). The Subscription's `configuration` can set a `threshold`:

```json
"evaluator": {"plugin_id": "alerts", "version": "0.3.0", "configuration": {"threshold": 0.6}}
```

The classifier returns a score from 0 to 1, the probability that the article fits. The article matches when its score reaches the threshold: 0.5 by default, between 0.2 and 0.95. Raise it for fewer, surer alerts.

## Read what matched

The Match's evidence names the classifier, its model, the score and the Parts it read:

```json
{
  "explanation": "Jev (jev-1.13.0) judged that the article fits the description: score 0.97, threshold 0.60.",
  "part_keys": ["title", "body"],
  "details": {"kind": "described", "classifier": "Jev", "model": "jev-1.13.0", "score": 0.97, "threshold": 0.6, "truncated": false}
}
```

`truncated: true` means the article was longer than what is sent, so the classifier saw only its beginning.

## Timing and cost

A described alert waits until the article's vectors are attached, a few seconds after it is searchable. Set `{"wait_for_enrichment": false}` in the Subscription's configuration to decide at once, and on a deployment that never computes vectors.

Each new article costs one TypeSafe request for all described alerts together, whatever their number or owners; Quivr asks each distinct description once. A request is split only when it would exceed TypeSafe's size limit. Every new article is judged against every active described alert that watches its source.

When TypeSafe is down or rate-limited, the alerts wait and are retried; keyword alerts on the same article wait too. When the key is refused, only the described alerts wait, and the plugin log says why. An alert is never dropped.

## Turn them on

These steps are for the operator who runs Quivr.

1. Put the key in the `alerts` plugin's environment: `TYPESAFE_API_KEY=<your key>`. Never put it in Quivr's configuration, in logs or in a repository.
2. List the kind in the `alerts` pin of Quivr's configuration:

   ```json QUIVR_CONFIG
   {"plugins": [{"manifest": "plugins/alerts/quivr-plugin.yaml", "endpoint": "http://127.0.0.1:9910",
     "kinds": ["keywords", "described"]}]}
   ```

3. Restart the plugin and Quivr. The plugin logs at startup whether described alerts are enabled.

Without a key, pin `"kinds": ["keywords", "meaning", "keywords_or_meaning", "keywords_and_meaning"]` for keyword and local meaning checks. Use `kind: meaning` for a local description and explicitly select `meaning_check: vectors` for every meaning check. This pin excludes `described`: it is refused at creation with `422 invalid_expression`, even with `meaning_check: vectors`. The kind list alone does not prevent a mixed expression from selecting Jev. The local stack uses this list by default; `make dev` adds `described` only when `TYPESAFE_API_KEY` is set in its environment.

## Keep the meaning check inside the installation

Use `alerts` version `0.3.0` with Plugin API `0.10.0` for a local meaning check. It compares the article's stored E5 vectors with a query vector computed when the Saved Query Version is created. A vector is a numeric summary of meaning. This backend never calls Jev or sends article text to TypeSafe; it uses the installation's served text space and the same query encoder as semantic search.

The following expressions are illustrative. Save one with the [Saved Query API](/guides/keyword-alerts#save-the-alert), then create a Subscription pinned to `alerts@0.3.0`:

```json
{"kind": "meaning", "meaning_check": "vectors", "description": "Labour strikes at ports and harbours"}
```

To combine it with a keyword tree, choose `keywords_or_meaning` or `keywords_and_meaning`. State `meaning_check` explicitly; `jev` selects the external service, while `vectors` stays local:

```json
{"kind": "keywords_and_meaning", "meaning_check": "vectors", "description": "Labour strikes at ports and harbours", "match": {"term": "port"}}
```

The plugin takes the highest cosine similarity across all text Parts and segments. This score is closeness, not a probability. The Match names the winning Part, segment, vector space, similarity and threshold. Configure `threshold` on the evaluator to change the default **0.80**.

That default comes from 156 neutral French/English article-query pairs, including translations: 16 relevant pairs and 140 unrelated pairs. It matches all 16 relevant pairs and rejects 129 unrelated pairs; 11 unrelated pairs still match. An English paraphrase scores 0.886641, a French translation 0.815391, and the football control 0.765448. Scores overlap, so tune the threshold on your own examples rather than treating it as a confidence score. The [plugin calibration notes](https://github.com/The-Vibe-Company/quivr-v2/tree/main/plugins/alerts/calibration) include every pair, the pinned model revision and a reproducible measurement command.

If article vectors are missing, the decision is `not_ready`, even with `wait_for_enrichment: false`. Quivr retries after `record.enrichment_available`; the existing Match identity prevents duplicate alerts. Query vectors remain fixed with their Saved Query Version. After switching a Corpus's served vector space, create a new Saved Query Version and migrate its Subscriptions to it; vectors from different spaces cannot be compared.

Operators can offer `meaning`, `keywords_or_meaning` and `keywords_and_meaning` without a TypeSafe key by adding those kinds to the plugin pin. The local stack offers them by default. Existing Subscriptions keep their pinned plugin version; use [evaluator migration](/run-quivr/upgrade-an-alert-rule) to move them to `0.3.0`.
