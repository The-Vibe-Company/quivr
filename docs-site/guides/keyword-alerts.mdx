A keyword alert fires when a new article matches a query such as `"harbour strike" AND (ferry OR port) NOT football`. Quivr records each catch as a Match with the words that matched, and sends it to your webhook. The first-party `alerts` plugin decides the matches.

## Prerequisites

- The `alerts` plugin pinned. The local stack pins it; elsewhere see [Pin a plugin](/plugins/pin).
- `QUIVR_API_URL` and a `QUIVR_API_KEY` with `monitoring:read` and `monitoring:write`, plus `content:write` to add the test article below.
- `QUIVR_DESTINATION`: the id of a webhook destination the operator configured for your Organization. Destinations live in Quivr's configuration, never in API requests. The local stack's `make env` sets one that delivers nowhere.

## Write the query

| You want | Write |
| --- | --- |
| A word | `strike` |
| An exact phrase | `"harbour strike"` |
| All of several words, anywhere | `harbour strike` or `harbour AND strike` |
| Any of several words | `strike OR walkout` |
| Not this word | `strike NOT football` |
| Grouping | `(harbour OR port) AND (strike OR walkout)` |
| Articles from one source | `source:wire` |

- Operators are written in capitals; `and`, `or` and `not` in lower case are ordinary words. `NOT` binds tighter than `AND`, which binds tighter than `OR`.
- Case, accents and punctuation are ignored: `greve` finds "Grève".
- Words match whole, and there is no stemming: `strike` does not find "strikes". List the forms you need, `strike OR strikes`.
- Terms search the `title` and `body` Parts.
- `source:`, `origin:` (`client` or `connector`), `producer:`, `connector:` and `connector_kind:` filter on metadata Quivr always has. Other names, such as `author:`, work once the operator maps them ([below](#filter-on-your-own-metadata)).

## Turn it into an expression

Quivr stores a query as a JSON tree, which it validates when you save the alert, so a mistake is refused at once instead of silently never matching. The plugin ships the parser. From a `quivr-v2` checkout:

```bash
cd plugins/alerts && python3 -m alerts.notation '"harbour strike" AND (ferry OR port) NOT football'
```

```json
{
  "kind": "keywords",
  "match": {
    "all": [
      {"term": "harbour strike"},
      {"any": [{"term": "ferry"}, {"term": "port"}]},
      {"not": {"term": "football"}}
    ]
  }
}
```

An application can also build the tree from a form: `all`, `any` and `not` map to "all of these words", "any of these words" and "none of these words".

## Save the alert

These requests use a Corpus of their own:

{/* runnable */}
```bash
curl -s -X POST "$QUIVR_API_URL/v0/corpora" -H "Authorization: Bearer $QUIVR_API_KEY" \
  -H "Content-Type: application/json" -d '{"name": "Port news", "idempotency_key": "guide-keyword-alerts"}' | jq '{corpus_id}'
```

{/* output */}
```json
{"corpus_id": "{{CORPUS_ID}}"}
```

```bash
export CORPUS_ID=<the corpus_id above>
```

The Saved Query holds the expression and the Corpora it watches:

{/* runnable */}
```bash
curl -s -X POST "$QUIVR_API_URL/v0/saved-queries" -H "Authorization: Bearer $QUIVR_API_KEY" \
  -H "Content-Type: application/json" -d @- <<EOF | jq '{saved_query_id, version_id: .current_version.version_id}'
{
  "idempotency_key": "harbour-strikes", "name": "Harbour strikes",
  "definition": {
    "corpus_ids": ["$CORPUS_ID"], "retrieval_profile": "default", "temporal_policy": "from_activation",
    "expression": {"kind": "keywords", "match": {"all": [
      {"term": "harbour strike"}, {"any": [{"term": "ferry"}, {"term": "port"}]}, {"not": {"term": "football"}}]}}
  }
}
EOF
```

{/* output */}
```json
{"saved_query_id": "{{SAVED_QUERY_ID}}", "version_id": "{{SAVED_QUERY_VERSION_ID}}"}
```

```bash
export SAVED_QUERY_ID=<the saved_query_id above> SAVED_QUERY_VERSION_ID=<the version_id above>
```

The Subscription turns it on, with the `alerts` plugin as evaluator. Give it an `owner` when the alert belongs to one of your application's users: Quivr echoes it on every Match and webhook, so you can route each alert, and `GET /v0/subscriptions?owner=user-123` lists that user's alerts.

{/* runnable */}
```bash
curl -s -X POST "$QUIVR_API_URL/v0/subscriptions" -H "Authorization: Bearer $QUIVR_API_KEY" \
  -H "Content-Type: application/json" -d @- <<EOF | jq '{subscription_id, owner}'
{
  "idempotency_key": "harbour-strikes-user-123", "name": "Harbour strikes",
  "saved_query_id": "$SAVED_QUERY_ID", "saved_query_version_id": "$SAVED_QUERY_VERSION_ID",
  "evaluator": {"plugin_id": "alerts", "version": "0.3.0", "configuration": {}},
  "destination_id": "$QUIVR_DESTINATION",
  "owner": "user-123"
}
EOF
```

{/* output */}
```json
{"subscription_id": "{{SUBSCRIPTION_ID}}", "owner": "user-123"}
```

```bash
export SUBSCRIPTION_ID=<the subscription_id above>
```

The alert judges articles that become searchable from now on. Earlier articles are never judged; to see what a query would have caught before saving it, use `POST /v0/subscription-previews`.

## Read what matched

Add an article that matches:

{/* runnable */}
```bash
curl -s -X POST "$QUIVR_API_URL/v0/records" -H "Authorization: Bearer $QUIVR_API_KEY" \
  -H "Content-Type: application/json" -d @- <<EOF | jq '{receipt_id}'
{
  "idempotency_key": "guide-alerts-strike",
  "source": {"corpus_id": "$CORPUS_ID", "namespace": "wire", "record_key": "strike-2026-10-03"},
  "content": {"kind": "manifest", "parts": [
    {"key": "title", "role": "title", "content": {"kind": "text", "text": "Harbour strike halts the ferry"}},
    {"key": "body", "role": "body", "content": {"kind": "text", "text": "The harbour strike stopped every ferry to the island on Friday."}}
  ]}
}
EOF
```

{/* output */}
```json
{"receipt_id": "..."}
```

Within seconds a Match appears, with its evidence:

{/* runnable retry */}
```bash
curl -s "$QUIVR_API_URL/v0/matches?subscription_id=$SUBSCRIPTION_ID" -H "Authorization: Bearer $QUIVR_API_KEY" \
  | jq '{items: [.items[] | {owner, explanation: .evidence.explanation, part_keys: .evidence.part_keys}]}'
```

{/* output */}
```json
{"items": [{"owner": "user-123", "explanation": "Matched \"harbour strike\" in title, body; \"ferry\" in title, body.", "part_keys": ["title", "body"]}]}
```

The explanation lists the terms that made the article match and the Parts where each was found. Terms under `NOT` are never listed. `evidence.details` has the same facts as JSON.

## Receive the webhook

For each Match, Quivr sends a `POST` to the destination's URL. The body only references what happened; fetch the Match with `GET /v0/matches/{match_id}` to read its evidence:

```json
{"event_id": "…", "type": "match.created", "schema_version": "1", "occurred_at": "2026-10-03T09:12:44Z",
 "references": {"match_id": "…", "subscription_id": "…", "subscription_version_id": "…",
                "record_id": "…", "record_version_id": "…", "delivery_id": "…", "owner": "user-123"}}
```

Verify the signature before you parse the body. Requests follow [Standard Webhooks](https://www.standardwebhooks.com/): the `webhook-signature` header holds an HMAC-SHA256 of `webhook-id`, `webhook-timestamp` and the raw body, keyed with the secret the operator configured for the destination.

Answer with a 2xx status to acknowledge. Timeouts, `408`, `429` and `5xx` answers are retried with exponential backoff, from 1 second up to 5 minutes, for 24 hours; any other answer stops the retries. Delivery is at least once, and a retry sends the same `event_id` and the same bytes, so deduplicate on `webhook-id`.

`GET /v0/deliveries/{delivery_id}` shows a delivery's state and its attempts.

When an article that matched changes, the Subscription gets a follow-up: `match.corrected` when a correction still matches (a new Match linked to the earlier one), `match.no_longer_matches` when it does not, and `match.withdrawn` when the article is withdrawn.

## Change or stop an alert

| To | Send, with an `idempotency_key` in the body | Effect |
| --- | --- | --- |
| Change the query | `POST /v0/saved-queries/{id}/versions`, then `POST /v0/subscriptions/{id}/versions` pointing at the new Version | The new query judges articles that arrive afterwards |
| Rename | `POST /v0/subscriptions/{id}/rename` | No new Version |
| Pause, resume | `POST /v0/subscriptions/{id}/disable`, `…/enable` | Articles that arrive during the pause are not judged |
| Delete | `POST /v0/subscriptions/{id}/delete` | Permanent; earlier Matches stay readable |

## Upgrade the alert rule without losing alerts

A Subscription Version fixes the query and alert-rule plugin version that judges each article. Moving a Subscription to a new Version affects future changes only. Evaluations already queued keep their original Version and plugin pin; a missing evaluator keeps retrying with `evaluator_unavailable`.

For a zero-loss upgrade, use a key with `plugins:admin` and the relevant Corpus grants:

1. Run the exact old implementation A and new implementation B concurrently at separate reachable endpoints. If the plugin is baked into an image, retain and run A's old code separately. Do not label B as A.
2. [Register, certify and activate B](/plugins/switch-plugins-without-restarting#upgrade-an-alert-rule). Dry-run `POST /v0/admin/subscriptions/evaluator-migrations`, inspect any refusals, then migrate the accepted Subscriptions in pages.
3. Keep A running until `GET /v0/admin/plugins` shows both its `subscriptions` and `pinned_work` at zero. Pinned work includes old triggers waiting to dispatch into evaluations; current Subscriptions alone do not prove that A has drained.

## Retire evaluations you cannot finish

Restore A to finish its evaluations without losing potential Matches. If you cannot restore it, you can explicitly abandon a bounded batch. Retirement does not judge an article: it records `evaluator_retired`, never `no_match`, and creates no Match or Delivery. Earlier Matches and Delivery history remain unchanged.

Use `plugins:admin` for backlog inspection, retirement and receipt reads. The API key's Organization and Corpus grants bound the work you can see or retire.

1. Inspect `GET /v0/admin/subscriptions/evaluation-backlog`. Its response has `items` with `plugin_id`, `version`, `pending`, `erroring`, `unavailable` and `retired`. Request `limit` up to 500; when `next_after` is present, pass it as `after` to continue. This cursor is the last `plugin_id@version` returned.
2. Dry-run `POST /v0/admin/subscriptions/evaluation-retirements` for the exact unavailable version, with a reason explaining why you are abandoning it. The request body below is illustrative, not a runnable request. Replace the version and reason with your operational decision:

   ```json
   {"key": "retire-alerts-batch-1", "plugin_id": "alerts", "version": "0.2.0", "reason": "The old implementation cannot be restored; accept losing potential matches", "dry_run": true, "limit": 100}
   ```

3. Inspect the selected items and `leased` count. Only pending evaluations whose latest error is `evaluator_unavailable` and whose leases have expired can close. Live leases, other errors and work not yet dispatched are not retired.
4. Send a real request with `dry_run: false` when you accept that loss. A dry run reserves no key and changes nothing; you may reuse its key or choose another. The batch limit defaults to 100 and cannot exceed 500.
5. Read the receipt with `GET /v0/admin/subscriptions/evaluation-retirements/{retirement_id}`. Preserve it for the operational record. The read requires grants covering the original request's Corpus scope, even for an empty batch; a missing or hidden receipt returns `404`.
6. Let old triggers fan out, wait for live leases to expire, then repeat dry-run/real batches with new keys until the old version's `pending` and `unavailable` are zero. Resolve other errors separately, and check the registry's `subscriptions` and `pinned_work` before removing A. Retirement is a batch, not a permanent policy against that version.

Backlog counts describe recorded work, not endpoint health: `erroring` counts pending evaluations with an error, `unavailable` counts those whose latest error is `evaluator_unavailable`, and `retired` counts those closed with `evaluator_retired`. A restored endpoint can still have recorded errors until evaluation runs again.

The receipt contains the full request body with normalized `limit`, `retirement_id`, `outcome`, `items`, `remaining` and `leased`. Each item keeps its original `subscription_id`, `subscription_version_id`, `sequence`, `corpus_id`, `record_id` and `record_version_id`. Real retirements also have `created_at` and an `event_id` per item. Each event is `evaluation.retired`, with `resource.kind=evaluation_retirement` and `resource.id=retirement_id`; dry runs have neither event IDs nor a creation timestamp.

`remaining` counts unavailable evaluations left after the batch, including live leases counted by `leased`. A dry run reports that remainder as if its selected items were retired. Within an Organization, replaying a real key with the same normalized request and Corpus scope returns the original receipt, not new work or refreshed counts. Changing the request or scope with that key returns `409 idempotency_conflict`. Even an empty real batch reserves its receipt, so use a new key for later arrivals.

## Filter on your own metadata

Names such as `author` or `category` depend on where your sources put that information, usually in a Version extension. The operator maps each name to a JSON Pointer in the `alerts` pin's configuration:

```json QUIVR_CONFIG
{"plugins": [{"manifest": "plugins/alerts/quivr-plugin.yaml", "endpoint": "http://127.0.0.1:9910",
  "configuration": {"fields": {"author": "/extensions/example.news/data/author",
                               "category": "/extensions/example.news/data/categories"}}}]}
```

A list field matches when one of its values does. A name the operator has not mapped never matches, and the plugin logs a warning.

## Timing

A keyword alert is decided as soon as the article becomes searchable, before its vectors are computed. Set `{"wait_for_enrichment": true}` in the Subscription's `evaluator.configuration` to wait for them.

To match articles by subject rather than by words, use [described alerts](/guides/described-alerts).
